# Model Council 总体项目目标

版本：1.0
整理日期：2026-09-01
状态：项目最高层目标，所有后续开发必须与本文件保持一致

## 一、项目初心

Model Council 的初心不是“同时启动更多模型”，也不是“把多个聊天窗口
放在一起”。

它要解决的是一个实际项目中的长期痛点：

> 用户拥有多个能力、速度、价格和工具条件不同的 Agent＋模型，但目前
> 必须自己判断谁适合做什么、自己打开和检查每个工具、自己搬运上下文和
> 文件、自己核对模型是否正确、自己发现登录或权限问题，也很难知道最终
> 成果究竟由谁完成、消耗了多少资源。

本项目的最终目标是把这些繁琐而容易出错的协调工作交给一个可信的本地
控制系统，同时保留用户对模型选择、数据外发、任务开始、文件修改、费用
和最终交付的决定权。

Model Council 应让“多个不同模型共同完成一个真实项目”从个人手工操作，
变成一套可配置、可检查、可追踪、可暂停、可恢复、可审查的工作流程。

## 二、最终用户体验

用户不应需要理解每个 Agent 的内部协议，才能让它们合作。理想流程如下：

```text
用户启动 Model Council
        |
        v
发现、登记或读取已有的 Agent＋模型配置
        |
        v
用户手动指定角色，或让系统根据能力/可用性/成本提出建议
        |
        v
系统启动、连接或附着所需 Agent
        |
        v
逐一检查每个 Agent 与模型
        |
        +--> 发现问题：按 Agent、Provider、Model、检查项报告错误
        |                 并给出修复建议；禁止进入任务阶段
        |
        v
全部必需成员就绪
        |
        v
管理员平台向用户发送“可以开始”的通知和任务开始请求
        |
        +--> 用户拒绝：保持待命，不执行项目任务
        |
        +--> 用户授权：冻结本次团队与任务范围，开始协作
        |
        v
管理员模型拆解任务并调度执行者
        |
        v
执行者通过结构化消息、摘要、Artifact 和审查结果交换信息
        |
        v
管理员仲裁冲突、整合成果，并提交最终交付物
        |
        v
用户查看交付物、来源、质量证据、用量、费用和未解决风险
```

用户可以把“管理员”设为当前已经打开并可用的 Agent＋模型，例如：

```text
codex + gpt-5.6-sol
```

也可以将其他已打开的 Agent＋模型设为管理员。执行者可以是：

```text
zcode + glm-5.3-flash
reasonix + deepseek-v4-flash
```

这些名称只是示例。系统不得把任何特定厂商、模型、CLI或桌面工具写死为
唯一实现。

## 三、系统要协调的对象

项目中必须明确区分四种身份：

### Provider

提供模型服务、认证、端点、用量或账单能力的一方。Provider可能是云端
厂商、代理/中继服务或本地运行时。

### Model

真正进行推理的模型。Model拥有能力、上下文、速度、价格和可用性等属性，
但不一定自己能启动、读文件或调用工具。

### Agent

承载模型并提供执行接口的工具或应用，例如CLI、App Server、桌面应用、
本地服务或远程Agent节点。Agent负责会话、工具和权限边界。

### Role

在本次项目中承担的职责，而不是固定的厂商身份。最低限度包括：

- `manager`：理解用户目标、拆解任务、分派、追问、仲裁和整合；
- `worker`：执行架构、研究、编码、测试、文档或其他专业任务；
- `reviewer`：独立检查结论、代码、证据、风险和遗漏；
- `integrator`：形成最终交付；它可以与manager相同，也可以单独配置。

同一个Agent＋Model可以承担多个Role，但系统必须记录每个Role在本次运行
中的实际身份。用户也可以要求关键角色必须由不同模型承担。

## 四、核心能力目标

### 1. 配置与角色管理

用户可以：

- 手动登记、编辑、启用或禁用Provider、Model和Agent；
- 选择manager、worker、reviewer和integrator；
- 为角色选择具体Agent＋Model；
- 使用`manual`、`auto`或`hybrid`模式；
- 锁定关键角色，防止系统悄悄替换；
- 设置能力、价格、延迟、权限、模型分离和预算约束。

自动模式只能提出或执行有证据支持的选择。它不能因为某个模型“看起来
适合”就假定该模型可用。

### 2. 启动与就绪检查

项目开始前，系统应能自动启动、连接或附着用户选定的Agent；不能自动操作
的桌面Agent必须允许用户手动确认。

每个成员的检查必须分项记录：

- Agent是否存在、可启动或可连接；
- 是否已登录或认证；
- 配置的Model是否确实是当前运行的Model；
- Provider端点是否匹配；
- Model是否在该Provider/Agent中可用；
- 所需权限是否满足；
- 版本、协议和工具能力是否满足；
- 连通性或最小探针是否通过；
- 费用和余额数据是否可获得。

`available`、`not_configured`、`not_logged_in`、`wrong_model`、
`permission_denied`、`version_mismatch`、`connectivity_failed`、
`manual_confirmation_required`和`unknown`等状态必须区分，不能都显示为
模糊的“失败”。

只要必需成员未就绪，系统就不能向模型发送项目任务。

### 3. 用户授权闸门

“全部检查通过”不等于“可以开始任务”。

系统必须先向用户说明：

- 本次使用哪些Agent＋Model；
- 每个角色的职责和权限；
- 将发送哪些上下文、文件或Artifact；
- 预计或已知的费用、预算和数据来源；
- 哪些操作可能修改文件、运行命令、访问网络或调用外部服务；
- 失败、超预算或成员不可用时如何处理。

只有用户明确许可，管理员才可以开始本次项目运行。授权必须绑定本次
团队、任务、上下文、权限、预算和停止规则；配置或范围发生变化后必须
重新确认。

### 4. 模型之间的受控互通

模型不直接获得彼此的全部会话记录。系统通过控制平面提供：

- 任务分配消息；
- 结构化结果；
- 问题与回答；
- 评审与反驳；
- 决策和取舍；
- Artifact及其哈希引用；
- 必要的摘要和未解决问题。

管理员模型负责认知协调，确定性程序负责身份、依赖、权限、并发、预算、
超时、重试、审批和持久化。

### 5. 成果来源与交付

每份交付物内部必须保留来源链：

```text
Provider -> Model -> Agent -> Role -> Task -> Artifact
```

还应记录贡献者、审查者和最终整合者。用户可以选择交付文件显示：

- `compact`：简洁来源；
- `detailed`：完整协作来源；
- `hidden`：不在交付正文显示。

`hidden`只影响用户看到的展示，不删除内部审计信息。

### 6. 用量、费用与余额

系统应展示每次调用、本次运行、项目和角色维度的：

- 输入、缓存输入和输出用量；
- 调用次数、耗时和失败；
- Provider报告费用；
- 根据价格表计算的估算费用；
- 用户设置的预算、预警和硬上限；
- Provider余额或余额不可用状态。

必须明确区分`actual`、`provider_reported`、`estimated`、
`manual`和`unavailable`。未知不能伪装成零，估算不能冒充账单。

### 7. 过程证据与恢复

系统应让用户能回答：

- 谁做了这项工作？
- 它使用了哪个模型和Agent？
- 它看到了哪些上游结果？
- 哪些结论经过独立审查？
- 哪些测试或证据支持最终交付？
- 如果中途失败，能否从安全检查点恢复？

涉及代码的任务必须支持隔离工作区、测试证据、差异审查和人工确认后的
合并。系统不得默认把模型输出等同于正确性。

## 五、不可偏离的原则

1. 用户是最终授权者；管理员模型不是最高权限者。
2. 认知平面与控制平面分离。
3. 不允许静默替换用户锁定的Agent或Model。
4. 不允许把模型清单存在误认为模型实际可用。
5. 不允许未经明确授权外发项目内容、路径、文件、凭据或派生私密信息。
6. 不向每个模型广播全部历史；只传递完成当前任务所需的最小上下文。
7. 真实写入、执行、网络、部署、合并和删除必须有独立权限边界。
8. 失败要可见、可定位、可恢复；不能用伪成功掩盖不确定性。
9. Provider、Model和Agent必须保持可替换，避免绑定单一厂商。
10. 所有重要决策、来源、预算和审批都应留下本地可审计证据。
11. 默认本地优先；运行时私密数据不得进入公共仓库。
12. 每个开发板块都必须说明它如何服务于本总体目标，以及没有改变哪些边界。

## 六、成功标准

项目达到目标，不是因为“能调用多个模型”，而是因为普通用户可以完成
下面的闭环：

1. 打开应用并看到已发现或已登记的Agent＋Model清单；
2. 手动指定管理员和执行者，或接受系统有依据的推荐；
3. 系统逐个启动/连接并报告每个成员的真实状态；
4. 某个成员有问题时，用户能知道具体是哪个Agent、哪个Model和哪个检查项；
5. 全部必需成员就绪后，用户收到清晰的开始请求；
6. 未获得用户许可前，不发送项目任务；
7. 获得许可后，管理员能让不同模型在边界内并行或顺序协作；
8. 模型可以通过结构化消息和Artifact引用互通成果；
9. 审查者能独立检查执行者的结果；
10. 最终交付清楚说明来源、证据、风险、用量和费用；
11. 用户可以暂停、拒绝、重试、恢复或结束任务；
12. 整个过程不会静默扩大数据、文件、网络或权限范围。

## 七、当前实现与最终目标的关系

当前仓库已经实现了大量“控制平面”能力：注册、路由、预算、来源、
启动准备、协议适配、审批、隔离工作区、审查恢复、本地Web界面和隐私
门禁。这些都是实现最终用户流程的基础，但它们本身不是项目初心。

后续开发必须持续回答：

> 这项改动是否让用户更容易、安全、可验证地配置并授权一组不同的
> Agent＋Model完成真实项目？

如果答案只是“增加了一个协议”“增加了一个模型调用”或“增加了一个
界面按钮”，却没有改善上述用户闭环、证据、边界或可恢复性，则它不应
自动进入主路线。

## 八、后续任务的防跑偏检查表

每个新板块开始前，必须写清楚：

- 服务于哪一项总体目标；
- 解决用户流程中的哪一步；
- 输入、输出和验收标准；
- 会增加什么权限或数据边界；
- 哪些事情明确不在本板块范围内；
- 失败时如何停止并留下证据；
- 如何做离线测试和隐私检查；
- 完成后是否需要新的用户授权。

每个板块完成后，项目报告必须包含：

- 对总体目标的贡献；
- 已实现和未实现的部分；
- 对用户体验的影响；
- 新增的安全、隐私和费用边界；
- 已验证证据；
- 下一板块为什么是必要的；
- 是否发现了需要写入本文件的新想法。

## 九、当前阶段判断

截至2026年9月1日，Model Council已经从离线MVP发展为具有较完整本地
控制能力的实验性产品，但仍不能被描述为“任意Agent＋任意Model开箱即用
地自动协作”。

当前最重要的不是无止境增加模型数量，而是围绕本文件完成三件事：

1. 把不同Agent＋Model的启动、检查、角色绑定和用户许可流程做成一致的
   用户体验；
2. 在真实项目边界内继续验证通信、来源、费用和权限控制；
3. 每次扩大真实调用范围时，都保持明确、可审计、可撤销的授权。
